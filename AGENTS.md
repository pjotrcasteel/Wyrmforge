## Unified engine rule (LOCKED)

**Pixel-first 2.5D rule (LOCKED, 29 October 2026):** WyrmForge is a mobile-first **2.5D pixel-art game**, not a 3D game rendered at low resolution. Every engine, lab, renderer, environment and asset workflow must preserve world-anchored 2.5D perspective, native pixel readability and 320/390px mobile presentation. Use sprite/tile/layer surfaces with optional elevation, normal/material maps and occluders; **no runtime 3D model, mesh-scene or 3D skeletal/physics pipeline may become a default engine prerequisite**. 3D math and **optional offline** Blender/rig authoring-to-sprite exports are allowed where justified; preserve already approved source work. **Do not delete or rewrite archived AN0–AN6 PR #387 (closed unmerged by owner on 30 October):** its optional source-skin GPU path is a shared-renderer 2.5D animation experiment, not a default requirement; retain source rigs, tests, fallback and approval gates. [Canonical AN closure and sprite-first direction](docs/canon/roadmap.md). Before introducing mandatory 3D, demonstrate that a simpler 2D/2.5D solution fails, compare real in-Hunt mobile captures and obtain explicit owner approval. Canon: [product identity](docs/canon/vision-and-story.md#11-product-identity--locked), [architecture](docs/canon/architecture-and-quality.md#locked--pixel-first-25d-runtime-contract-29-october-2026), [art](docs/canon/art-and-animation.md#pixel-first-authoring-and-gameplay-output--locked-29-october-2026).


Before starting or continuing an engine, follow the [mandatory 2.5D pixel-art milestone acceptance matrix](docs/canon/roadmap.md#locked--actual-25d-pixel-art-acceptance-for-every-visual-milestone-29-october-2026): native sprite scale and sampling, shared camera/feet/occlusion, material/atlas parity, in-Hunt 320/390px real captures and actual phone budgets. This is an additional gate, not a reason to regress the approved AR0–AR3 solid-color geography foundation, revive archived AN PR #387, or modify active G PRs. Then read [the canonical one-engine-per-responsibility rule and ENG0–ENG4 migration gate](docs/canon/roadmap.md#locked--one-reusable-engine-per-responsibility-owner-decision-27-october-2026) and [C# gameplay/event ownership](docs/canon/architecture-and-quality.md#locked--unified-engine-ownership-and-event-authority-27-october-2026). Reuse existing engine contracts for lighting, AI, animation, cosmetic physics, VFX and audio; do not add per-spell/monster/scene engines or transfer C# gameplay authority to presentation. For unrelated feature-engine extensions, owner-approved Hollowed improvements precede the ENG0–ENG4 consolidation checkpoint. **Explicit 29 October 2026 owner override, completed checkpoint 31 October: AR0–AR3 map-to-arena geography, navigation, exploration and semantic height/terrain were independently authorized, owner-approved and merged (#404/#457/#458). AR4–AR5/WF32 composition may continue after AR3 approval; they are not blocked by G6–G10 Lighting 1.0 or by the Hollowed art gate.** These are world-generation/site contracts using the existing C# simulation and current live arena renderer, not a new physics, lighting or animation engine. See the canonical [AR execution exception](docs/canon/roadmap.md#world-authored-arenas-and-groundmaterial-fidelity--ar0ar7-owner-decision-29-october-2026-locked) and [Work handover](docs/handover/2026-10-29-arena-world-first-work-execution.md). G5 is only Lighting 0.1 opt-in world composition; G6–G10 target Lighting 1.0, and default non-Town GPU cutover is G10. One coherent commit is a checkpoint, **not** a reason to stop work and request “continue”; keep pushing and validating until the assigned unblocked milestones are complete.

## Git checkpoints

The owner explicitly requires frequent remote checkpoints after repeated loss of unpublished work.

- Commit and push each coherent slice to a task branch before starting another slice.
- Push a checkpoint before long visual generation, capture, or validation work. A local commit alone is insufficient.
- Keep unfinished work on a clearly described draft PR; merge only validated changes.
- Verify the remote branch head after uploading. Record implementation status, remaining work and evidence in repository documentation.
- Do not describe incomplete art or missing validation as finished. Preserve source assets as well as runtime atlases.
